@shimishige @addisonhoward 
Thank you for providing the game engine codes.
I believe there is a bug in ToolCountProc (the routine that discards a "Team Rocket only" Energy card when it ends up attached to a non–Team Rocket Pokémon).  This is rarely triggered, but a player who is likely to lose could deliberately cause a crash.

In line 1149-1179 of EffectProc.h

The outer loop iterates over both players and binds ps to the loop player, but the inner Energy loop reuses the same variable name i, shadowing the player index. As a result, the MoveCard call falls back to activePlayerIndex() for the player argument instead of the owner of the Energy:

```
for (int i : state.basicPlayerOrder()) {          // i = player index (both players)
    const PlayerState& ps = state.players[i];
    ...
    for (int i = ps.energy.size() - 1; i >= 0; i--) {   // this i shadows the player index
        CardRef ref = ps.energy[i];
        const Card& card = state.getCard(ref);
        const CardMaster& master = card.getMaster();
        if (master.onlyTeamRocket) {
            RefPosition rp = state.attachedCardPosition(card);
            if (!state.getCard(rp.ref).getMaster().teamRocket) {
                state.stateChanged = true;
                MoveCard(state, state.activePlayerIndex(), AreaType::Energy, i, AreaType::Trash);
                //             ^^^^^^^^^^^^^^^^^^^^^^^^^^ should be the owner of the Energy, not the active player
            }
        }
    }
}
```
Here ps is players[<outer i>] (the Energy's owner), but MoveCard receives activePlayerIndex() as the player index and i (now the Energy index) as the from-index. Since basicPlayerOrder() visits both players regardless of whose turn it is, when the Energy being checked belongs to the non-active player, this:

1. Trashes an Energy from the wrong player's board, and
2. Indexes players[activePlayerIndex()].energy with an index that is only valid for the other player's Energy list — if that index is out of range, getCardRef does energy.at(index) and throws, crashing the game.

Suggested fix

Rename the inner loop variable and pass the owner's player index:
```
for (int j = ps.energy.size() - 1; j >= 0; j--) {
    CardRef ref = ps.energy[j];
    const Card& card = state.getCard(ref);
    const CardMaster& master = card.getMaster();
    if (master.onlyTeamRocket) {
        RefPosition rp = state.attachedCardPosition(card);
        if (!state.getCard(rp.ref).getMaster().teamRocket) {
            state.stateChanged = true;
            MoveCard(state, i, AreaType::Energy, j, AreaType::Trash);
        }
    }
}
```

Visualizer Replay Bug: selected actions are shifted by 1 step (off-by-one)

Hi everyone,

While working on offline behavioral cloning and log analysis using the visualizer replay files (the JSON files in list format), we discovered a critical bug in the C++ simulator engine's serialization logic. This bug was successfully analyzed, and the following solution was proposed by Gemini 3.5 Flash during our pair programming session.

The Problem
The chosen actions in the "selected" key are shifted by 1 step.

Because of this shift, entry[0].selected (the initial coin flip / first-player decision) is always recorded as null.
The actual choice for entry[0] is stored in entry[1].selected.
The actual choice for entry[1] (e.g. setting up active Pokemon) is stored in entry[2].selected, and so on.
The very last action of the match is written into a dummy terminal step at the end.
If you are using local visualizer replays to train your policy models offline, this shift introduces significant noise (essentially training the model to predict the previous turn's action in the current state).

Root Cause
In Export.cpp, inside GetBattleData, the step is serialized with data->selected from the previous step because the state has already advanced to the next step (following data->next() in Select).

```python
cpp
// Export.cpp - Old buggy code:
if (data->preGetSelectCount != data->selectCount) {
  const State& state = data->state;
  int index = std::max(state.logIndex[0], state.logIndex[1]);
  const std::vector<int>* selected = nullptr;
  if (data->visData.size() > 0) {
    selected = &data->selected;
  }
  ToJsonVis(data->state, data->jsonBuilder, index, selected);
  data->visData.push_back(data->jsonBuilder.buf);
  data->preGetSelectCount = data->selectCount;
}
```
Proposed Fix
To fix this, the steps should be serialized to visData at the moment the decision is actually made inside ApiSelect (Api.h), right before calling data->next().

In Api.h, inside ApiSelect (before data->next()):
```python
cpp
int index = std::max(state.logIndex[0], state.logIndex[1]);
ToJsonVis(data->state, data->jsonBuilder, index, &data->selected);
data->visData.push_back(data->jsonBuilder.buf);
```
In Export.cpp, change GetBattleData to only append the final terminal step when the match finishes:
```python
cpp
GAME_API SerialData GetBattleData(ApiData* data) {
  if (data->apiDataType != 1) {
    return {};
  }
  if (data->state.isFinish() && data->visData.size() == data->selectCount) {
    const State& state = data->state;
    int index = std::max(state.logIndex[0], state.logIndex[1]);
    ToJsonVis(data->state, data->jsonBuilder, index, nullptr);
    data->visData.push_back(data->jsonBuilder.buf);
  }
  return ApiGetBattleData(data);
}
```

Hope this helps anyone doing offline training or writing custom local analyzer tools!
