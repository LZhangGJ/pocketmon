# Proposal: an official API extension for simulation / search-based agents

*(English first; 日本語は下にあります)*

## TL;DR
In the Pokémon TCG you take several uncertainty-bearing actions in a single turn. Especially around draws, the game branches a lot ("if I draw this, then I do that"). When you try to implement search over multiple plays (e.g. MCTS), the current API makes this hard. To enable stronger solutions, I'd like to propose an API to shuffle the deck at an arbitrary point during a Search.

## Background / Motivation
As an example, take Alakazam (the Psychic Draw ability), which is in the current environment. It is often paired with Dudunsparce (Run Away Draw) and is a typical deck that repeats several draws in a single turn. Meanwhile, the card pool contains hand-disruption cards such as Unfair Stamp and Judge. Against those, deliberately NOT using Dudunsparce's ability and keeping cards in hand (to play around Unfair Stamp) can be the correct play.

Consider the decision of whether to use Dudunsparce's ability *after* Psychic Draw:
- Psychic Draw gives you the card you need → don't use Dudunsparce
- Psychic Draw doesn't → use Dudunsparce to dig further

That is the natural decision. However, because the deck order is already fixed before Psychic Draw, a search-based algorithm can decide while **already knowing** what using Dudunsparce would draw. That is,

- in a deck order where "using Dudunsparce hits the card" → use it
- in a deck order where "using Dudunsparce misses" → don't use it (do something else)

so the search can optimize *after seeing* the fixed deck order (clairvoyance), which overestimates the true expected value. To avoid this, we need an API that shuffles the deck after Psychic Draw and issues a new SearchId.

## Observed behavior (black-box)
- Issuing a top-of-deck draw (e.g. a draw ability) from the same SearchId is deterministic.
  - Measured: Lunar Cycle from the same SearchId ×8 → drew the identical 3 cards every time. Re-determinizing the root (SearchBegin with a different deck order) ×8 → 8 different draws.
- When a shuffle happens, the (new) deck order is fixed at that moment.
  - Cards like Lillie's Determination shuffle before drawing, so re-stepping the same move gives a different result (it is re-rolled).
- Going deeper / branching within a search is unrestricted (SearchStep), but you cannot start a fresh search with a new deck order mid-way (no SearchBegin / re-determinization from a mid-search state).
  - Measured: search_begin_input is only present on a real battle observation (even the root SearchState's observation, and every stepped state, is None); calling SearchBegin on a mid-search observation fails with `ValueError: Not agent observation.`

## Request to the organizers
I propose adding a feature to shuffle the deck at an arbitrary point during a Search.
Note: the card pool also contains effects that fix the top/bottom of the deck (e.g. Ciphermaniac's Codebreaking / Dusk Ball / Drakloak's Recon Directive), so it would be ideal if the shuffle range could be limited too.
Without this, participants who want to search would have to reimplement the whole simulator for all cards themselves, which would significantly raise the barrier to entry.

- This is only what I found on my own; apologies if I have missed anything.
- This is my first Kaggle competition, so if this kind of proposal is inappropriate, I will delete the post.
- The English section was drafted with Claude Code, so apologies if any parts read awkwardly.

# （日本語）シミュレーション・探索実装に向けた公式 API 拡張の提案

## TL;DR
ポケモンカードでは不確実性を伴う行動を1ターンに複数回行う。特にドローを伴うプレイをしたときに、「これが引けたらこれをする」のような分岐が多く発生するゲームである。
MCTS を始めとした複数のプレイに対する探索を行う際、今の API ではこの探索を実装することが難しい。
より強い解法の探求のためにも、Search 中の任意タイミングでの山のシャッフル機能の実装を提案したい。

## 背景 / 動機
例として現状の環境にいるフーディン（特性サイコドロー）を挙げる。このデッキはノココッチ（特性にげあしドロー）と組み合わせていることが多く、特に一度のターンに複数のドローを繰り返す典型的なデッキである。
一方、現在のカードプールにはアンフェアスタンプやジャッジマンなどのハンド干渉を行うカードが存在する。この場合、ノココッチの特性を使わずにあえて残してアンフェアスタンプに備えるというプレイが正当化される。

ここではサイコドローをしたあと、ノココッチの特性を使うかどうかという問題を考える。

- サイコドローをして必要なカードが引ける → ノココッチの特性を使わない
- サイコドローをして必要なカードを引けない → ノココッチの特性を使ってさらに引けるかを試行する

となるのが自然ではある。しかしサイコドロー以前に山の順番が固定されているため、探索ベースのアルゴリズムでは「ノココッチの特性を使ったら何が引けるか」を **すでに知った上で** 判断できてしまう。すなわち

- 「ノココッチを使えば当たり札を引ける」山順 → 使う
- 「ノココッチを使っても当たり札を引けない」山順 → 使わない（別の手に回す）

のように、固定された山順を見てから最適化（透視 / clairvoyance）でき、実戦の期待値を過大評価してしまう。
これを避けるために、サイコドロー後に山をシャッフルして新たな SearchId を発行するような API が必要となる。

## 検証した挙動（ブラックボックス）
- 同じ SearchId に対し、山の上から引く系（ドロー特性など）を発行すると決定的な動作になること
  - 実測: 同じ SearchId からルナサイクルを 8 回 → 引いた 3 枚は毎回同一。root を re-determinize（別の山順で SearchBegin）×8 → 毎回別の 3 枚。
- 山のシャッフルが行われると、その時点で（新しい）山の順番が決まること
  - リーリエの決心などはドロー前に山をシャッフルするため、同じ手を踏み直すと別の結果になる（再抽選される）
- 探索を深く進める／枝分かれするのは自由（SearchStep）だが、**探索の途中から新しい山順を与えて探索し直す（SearchBegin による re-determinize）ことはできない**
  - 実測: `search_begin_input` は本物の対戦観測にしか付かない（root の SearchState の観測も、その先の途中状態も None）。途中状態に SearchBegin を呼ぶと `ValueError: Not agent observation.` で弾かれる。

## 運営への要望
Search 中の任意タイミングでの山のシャッフルができる機能を実装することを提案する。
なお、カードプールには暗号マニアの解読やダークボール、ドロンチの特性ていさつしれいなど、山の上下を固定するようなテキストが存在するため、シャッフルする範囲も限定できることが望ましい。

これがない場合、（探索を行う参加者は）全カードに対するシミュレーターを自前実装する必要が生じてしまい、参入障壁を大きく高めることにつながると考えられる。
