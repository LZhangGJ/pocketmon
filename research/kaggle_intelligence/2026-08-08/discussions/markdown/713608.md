# What We Tried, What Ceilinged, and Two Questions We Can't Answer Alone

*A detailed account of PTCG AI work — including every dead end — and two open technical questions we'd love community input on.*

---

## TL;DR

Our best confirmed-shippable agent is a **neuro-symbolic Mega Starmie ex** policy on keidroid's LB #1 60-card list, scoring **54% META** on a competition-calibrated frequency-weighted field (Lucario 42%, Crustle 15%, Trevenant 15%, Bellibolt 8%, Other 10%). That is **2.4× our best Alakazam result (22.6%)** on the same field.

We also have an **opp-belief-gated search hybrid at 59.7% META** (+5.7pp) that we believe is correct — but it depends on forward-search being available at submission time, and we have not been able to confirm that. That's one of the two questions at the end of this post.

The Lucario matchup is 29% with our best policy. At 42% of the field, it determines everything. That's the other question.

---

## 1. The Problem Setup

The `cabt` engine exposes one interface: `agent(obs) -> list[int]`. The engine enumerates every legal play in `obs["select"]["option"]`; the agent returns a list of **indices** into that menu. You never construct an action; you rank and pick from a pre-generated list.

This matters more than it sounds. A naive early version of our codebase modeled the game as "build an attack/attach action" and had to be scrapped entirely. Every method below operates on the real interface: score the offered options, return the best index set.

Two empirical facts about the engine shaped everything:

- **The engine enumerates options in a strong best→worst order.** Just returning `[0]` ("B1" in our shorthand) beats random ~88–90% and is a genuinely difficult local optimum to escape. A naive type-priority reorder of the menu *lost* to B1 (3.3% vs first-index in our tests).
- **No seed hook.** The compiled engine's `BattleStart` takes only the 120 card IDs; there is no RNG seed exposed to Python. Every evaluation is independent-sample. This is a significant variance problem we'll return to.

## 2. The Approach That Actually Works

### 2.1 Copy the LB #1 deck

The single highest-value decision in the project was extracting keidroid's exact 60-card Mega Starmie ex list from `episodes.db` (`ep_player.deck_json`, 78 winning games all used the same variant) and piloting it with an existing strong heuristic (`StarmiePolicy`).

Result: **54.0% META** at N=1,200 games (σ=1.4pp). Per-matchup breakdown:

| Matchup | Weight | Starmie WR |
|---|---|---|
| Lucario | 42% | 29.0% |
| Crustle | 15% | 39.0% |
| BaseTrev | 15% | 82.9% |
| PetrelTrev | 10% | 80.6% |
| Bellibolt | 8% | 68.5% |
| Other | 10% | 100% |
| **META** | | **54.0%** |

keidroid's real ladder record on this deck (from our episode database): 78W / 38L = 67.2%. We close 54% of that gap with a heuristic policy alone. The remaining 13pp is what keidroid knows that we don't.

### 2.2 The opp-belief-gated hybrid

1-ply forward search (`search_begin/step`) hurts Starmie on Lucario (29% → 22%, −7pp) but is enormous on Crustle (39% → 83.5%, +44.5pp). The fix is gating by opponent identity: use `agent/opp_belief.py` (Bayesian archetype ID from observed bench cards) to default to pure StarmiePolicy, then switch to search-wrap **only once the opponent is confidently non-Lucario** (conf ≥ 0.60).

The direction matters. We tried the reverse — default search, switch to pure on Lucario — and it failed at 57.0% because switching search → pure mid-game after a search-poisoned opening doesn't recover the Lucario WR. Defaulting to pure fixed it:

| Variant | META | Lucario | Crustle |
|---|---|---|---|
| pure StarmiePolicy | 54.0% | 29.0% | 39.0% |
| always 1-ply search | 57.1% | 22.0% | 83.5% |
| hybrid v1 (default search) | 57.0% | 20.1% | — |
| **hybrid v2 (default pure)** | **59.7%** | **24.5%** | **86.0%** |

**The hybrid is our best agent.** But it calls `search_begin/step` natively. Whether the Kaggle runtime exposes a working forward-search API at submission time is unresolved — see §5b.

## 3. Everything We Tried and What Each Ceiling Taught Us

### 3.1 The pre-transformer plateau (~9 methods, same ceiling)

Before the current agent, we exhausted roughly nine approaches against the Alakazam "Powerful Hand" deck:

| Method | Result vs B1 mirror | Lesson |
|---|---|---|
| 1-ply hand-crafted search | ~40% | ≤ B1 |
| 2-ply expectimax | ~50% | ≤ B1 |
| ISMCTS / AlphaZero-lite | 42.5% → 50% | Parity, never past |
| MLP self-play | ~52–67% | Feature ceiling |
| FSP pool (vs checkpoints) | 46.5% vs B1 | Worse than mirror self-play |
| Demo-RL (POfD-style) | Degrades | Representation wall |
| Static heuristic reorders | 2–20% | Native order is too strong |
| ~10 hand-built decks | All < sample deck | Deck was the lever, not the pilot |

The pattern: every method plateaued around the same point and never robustly cleared B1. The failures were not capacity failures (a 256-wide MLP did no better than 64-wide). They were representation failures — none of these methods encoded *which card* an option was, only its type and damage. The network literally could not see card synergies.

The lever that broke through was architecture: a **card-embedding multi-head transformer** (DMODEL=64, NHEAD=4, NLAYERS=2) where each option token is a concatenation of a role one-hot, a **per-card identity one-hot over the full card vocabulary**, and a 15-dimensional scalar block. Card identity is the lever nine prior methods lacked. The transformer reached 73–74% vs B1 mirror (revalidated at 400+ games), the first architecture to break the ~68.5% feature ceiling.

### 3.2 Beam search: +11.3pp on a weak heuristic, −15pp on a strong one

We replicated the MultiPly agent's deterministic beam search (width=3, depth≤4, 1.5s budget) over the Alakazam heuristic:

**Alakazam heuristic (10.7% META) + beam → 22.0% META = +11.3pp** (N=1,200, z≈5.7, confirmed at N=2,988 as 22.6%).

The same beam on **StarmiePolicy (54.0% META) → 38.6% META = −15.4pp** (z≈7).

The beam's crude leaf eval (prize_diff×10000 + energy×120 + hp terms) overrides StarmiePolicy's nuanced tempo play with greedy prize-grabbing, degrading a strong policy. **Beam value is inversely proportional to base-policy quality.** Wrap weak heuristics; leave strong ones alone.

Latency: ~8.6ms per MAIN decision. The Kaggle budget is not the bottleneck.

### 3.3 Imitation (BC / DAgger) plateaus below the teacher

We ran 8 DAgger iterations (400 DAgger + 100 anchor rollout games/iter, 64d transformer, teacher = AlakazamPolicy heuristic):

| Iter | Clone accuracy | H2H vs heuristic |
|---|---|---|
| 1 | 96.6% | 33.3% |
| 3 | 98.2% | 41.0% |
| 4 | **99.0%** | **28.0%** (OVERFIT — highest clone, worst H2H) |
| 5 | 96.4% | **41.3%** (best checkpoint) |
| 7 | 96.2% | 33.3% (declining) |

The plateau is ~41% H2H; the teacher wins 59-41. Iter 4 is textbook covariate-shift inversion: clone accuracy peaks exactly when H2H collapses. The plateau reproduced independently in a second baseline run (iter 4: 28.7%, matching run 1's 28.0%). This is a structural property, not noise.

**Pure imitation cannot pass a heuristic teacher.** To exceed the heuristic you need search on top of it, or RL self-play generating super-teacher trajectories. We tried both. Search won (+11.3pp for Alakazam). RL did not produce a measurable gain — but the reason for that is informative:

### 3.4 The RL plateau is a measurement limit, not an algorithmic one

For weeks, every RL A/B on the Alakazam track returned ambiguous results. Eventually we instrumented why.

A **privileged critic probe** (logistic regression, n=6,211 self-play games) showed:
- NN value head AUC: **0.61**
- 10-feature linear model on the **public** board state: AUC **0.818** (0.69 even on turns 1–4)
- Adding the opponent's hidden hand: AUC **0.825** — delta **+0.007**

So the outcome is not irreducibly noisy, hidden information is not the bottleneck, and a trivial linear probe nails a signal the 64d value head was underfitting during training.

We substituted the AUC-0.82 linear board critic as the GAE baseline (`engine/board_critic.py`). The A/B from the same BC seed: vsR8 climbed 12% → 18–20% and then flatlined while the held-out hard score eroded. The 12→18 jump is **indistinguishable from noise at N=120** (±16pp at that sample size). A verified-good baseline could not be shown to help, because the RL evaluator sits below its own noise floor.

To confirm the head is not representationally broken, we ran an **overfit-one-batch probe** (`tests/probe_value_head.py`): the real 64d HL-Gauss value head trained on 64 synthetic boards under three signal types (random labels, scalar within the readout token, scalar routed through attention). All three converged to **correlation 1.000** in hundreds of steps. The head can represent any board signal — the 0.61 is not capacity or a broken readout. It is **sparse, terminal-only self-play return targets evaluated through a noisy evaluator.**

Three independent probes (privileged critic, board critic A/B, overfit batch) converge: **the bottleneck is data and measurement, not the network or algorithm.** Until we have a paired, low-variance evaluator (N≥500, fixed decks, ideally common random numbers — which the engine doesn't expose), no RL A/B is interpretable. This is why RL stays in the writeup as a methodology contribution rather than a WR lever.

### 3.5 The forensic loss-analysis trap

We captured 40 losing games and had an LLM analyze them. The analysis was genuinely insightful — it correctly identified bench-out losses (15/40) and surfaced three crisp fixes: retreat a low-HP active to deny a prize, never attack for 0 damage when a setup play exists, don't evolve your only basic with an empty bench.

We implemented all three as guards and ran a paired A/B (n=250/matchup):

| Matchup | Live guards | + 3 forensic guards | Δ | p |
|---|---|---|---|---|
| Mirror | 59.2% | 51.6% | −7.6 | 0.07 |
| TopBot | 64.0% | 52.4% | −11.6 | **0.012** |
| Anti-Crustle | 33.2% | 29.6% | −3.6 | 0.40 |
| **Pooled** | **52.1%** | **44.5%** | **−7.6** | **0.003** |

The "fixes" made the agent significantly worse. **Survivorship bias:** reading only losses makes "stay in at 30 HP and attack" look like a mistake — but the losing traces hide every game we won by grabbing a prize before dying. The policy's instinct is correct *on average*. Had we trusted the compelling narrative without the A/B, we would have shipped a ~7.6pp regression.

## 4. Eval Discipline (the lesson we had to learn the expensive way)

Three eval failures burned us:

1. **Short-eval inflation.** A "77%" training metric at 200 games was 67% at 400 games. The 128-dim "big net" hit 74% at 200 games, 66.8% at 400 games. Rule: revalidate at ≥400 games before trusting any result.

2. **Hill-climbing below the noise floor.** We hill-climbed 68 heuristic config weights for Alakazam and watched the "best" go 0.786 → 0.861 → 0.921 over rounds. Suspicious. When we re-evaluated the *identical* config byte-for-byte (`CURRENT` vs `R8`) at 2,000 games, we got **0.8665 vs 0.8802 — a 1.37pp gap from pure sampling noise.** The hill-climber's accept threshold was 0.5pp. Every "improvement" from R5 onward was reading noise. Honest Alakazam WR: ~0.88, not 0.92.

3. **No Common Random Numbers.** Because the engine exposes no seed hook, every A/B is independent-sample. This forces sequential testing (SPRT-style) and larger N than paired experiments would need. For future comparisons in this competition: if you have CRN working, we'd love to hear how.

## 5. Where We'd Love Your Input

### 5a. The Lucario wall — 29% structural loss, 42% of the field

Our Starmie is 29% vs Mega Lucario ex. Since Lucario is 42% of the field weight, raising this matchup even 5pp would add more to META WR than any other lever.

What we've tried:
- BC clone of keidroid's decisions: **36.0% META, −18pp worse** than the heuristic in every matchup. 55% clone accuracy compounds into bad states.
- Beam search: hurts Lucario specifically (29% → 22%) because the crude leaf eval overrides Starmie's setup play.
- Tuning StarmiePolicy's Lucario sub-weights: marginal gains only.

The structural problem: Mega Brave hits for **270 damage**, enabling turn OHKOs. Starmie ex (250 HP) dies in one hit once Lucario is charged. The tempo race is extremely tight.

**Questions for the community:**
- Has anyone found a Starmie line against Lucario that isn't just "win the speed race"? Specific cards, energy sequencing, or tech slots?
- keidroid apparently cracks this matchup at 67% ladder WR. We have his 1,534 decisions in our DB but extracting the Lucario sub-policy from 78 games has been noisy. Has anyone had success mining per-matchup decision data at that sample size?
- Is there a non-ex attacker tech in the Starmie shell that changes the Lucario matchup structurally the way Hariyama changes the Crustle matchup?

### 5b. Does the Kaggle runtime expose a working forward-search API?

The observation dict includes `search_begin_input`. The `cg.sim.lib` native module exposes `search_begin` / `search_step` / `search_release` functions. Our hybrid agent (59.7% META, +5.7pp over raw) calls these.

Our ship-gate for the hybrid is unresolved: **we do not know if the Kaggle evaluation harness actually runs `cg.sim` at submission time.** The native cg module is NOT available on the pip `kaggle-environments` package, which has a different card-ID universe entirely. We built a cg shim (`build_cg_shim.py`) for the submission tarball that strips the native search functions — meaning `starmie_raw` (54%) is the confirmed-shippable agent, and `starmie_hybrid` (59.7%) is blocked on this question.

**Concrete question:** Has anyone confirmed that `search_begin` / `search_step` work correctly on the Kaggle evaluation harness? Or does the runtime use a shim that stubs out the search functions? If you've used forward search in a submission that validated and actually ran, we'd love to know.

### 5c. Variance reduction without an engine seed

Given the no-CRN constraint, our best current evaluation practice is:
- N=1,200 per arm (σ=1.4pp per matchup at that N) for single-matchup comparisons
- Sequential testing (SPRT-style) for go/no-go decisions
- Revalidating any result that looks like a gain at ≥400 games before acting on it

Is there a better approach in this engine? We thought about submitting two fixed-seed games via the obs `seed` field but couldn't find a seed hook in the BattleStart interface. If you've found a way to reduce eval variance without CRN, we'd like to hear it.

All the infrastructure built during this project is in the repo and reproducible:

- `engine/bench/bench_meta_weighted.py` — competition-calibrated frequency-weighted field evaluation
- `engine/pilots/starmie_hybrid_pilot.py` — the opp-belief-gated search hybrid
- `agent/opp_belief.py` — Bayesian archetype ID from observed board state
- `engine/pilots/ala_beam_pilot.py` — beam search over heuristic (the Alakazam version)
- `engine/tools/privileged_critic_probe.py` + `data/board_critic_logistic.json` — AUC-0.82 linear board evaluator (reusable as a Texel-tuning target or GAE baseline)
- `tests/probe_value_head.py` — deterministic overfit-one-batch probe for RL value head sanity
