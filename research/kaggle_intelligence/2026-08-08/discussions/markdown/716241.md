Hi everyone,

We found one replay where **Rare Candy** (`ふしぎなアメ`, cardId `1079`) appears to be consumed without performing the selected evolution.

In this case, the engine offers a Rare Candy skip-evolution as a legal option, the player selects that option, and the Rare Candy is discarded. However, no evolution event is emitted, and the target Pokémon remains a Basic Pokémon.

We would appreciate confirmation from the organizers on whether this is intended simulator behavior or a possible engine bug.

---

## TL;DR

In one recorded `cabt` replay, a player plays **Rare Candy** to skip-evolve a Basic Pokémon into a Stage 2 Pokémon.

The engine:

1. offers the evolution as a legal option,
2. the player selects it,
3. consumes the Rare Candy,

but then the engine does **not** perform the evolution.

Across **660** Rare Candy skip-evolution events in our replay corpus, this happened **exactly once**. Every other event, including cases with the same deck, the same card, and the same observable signature, evolved correctly.

From the observation-level data available to us, we could not find any observable game-state feature that distinguishes this non-evolving case from correctly-evolving cases. This appears more consistent with a rare internal-state-dependent engine issue than with a normal rules edge case, but we cannot confirm the root cause without engine source or state injection.

* **Card:** `1079` ふしぎなアメ / **Rare Candy**
* **Expected behavior:** the selected Basic Pokémon should evolve into the chosen Stage 2 Pokémon.
* **Observed behavior:** Rare Candy is consumed, but the Pokémon is **not** evolved.

## Why this looks like a possible bug

The engine itself offered the evolution as a legal option:

```text
select.context = 37
option type = 9
```

The player selected that option.

Given that, the engine seems internally inconsistent in this replay:

* either the evolution should not have been offered,
* or, once selected, the evolution should have been performed.

Consuming Rare Candy while silently skipping the selected evolution does not seem consistent with either behavior.

The target also appears to be a valid Rare Candy target from the observable state:

* it is a Basic Pokémon,
* it has a matching Stage 2 Pokémon in hand,
* `appearThisTurn: false`,
* and the engine offered the evolution option.

In our replay corpus, **659 of 660** Rare Candy events evolved correctly, including events involving this same card and the same deck.

We then tried to find any observable feature that separates this case from the 659 correct cases. Every candidate feature we tested was refuted by at least one correctly-evolving counterexample with the same value.

## Why ordinary per-event randomness seems unlikely

We do not think this is ordinary per-event randomness.

Rare Candy resolution is not a coin-flip or shuffle mechanic. Also, if this were caused by an ordinary randomized branch in Rare Candy resolution, we would expect to see more than a single isolated case across 660 events, unless the branch probability is extremely small.

Each replay is also a deterministic recorded `kaggle-environments` replay.

The observed pattern is:

```text
1/660 cases
same observable signature as correct cases
not explained by any tested observable feature
```

This makes the issue look more like a rare internal-state-dependent engine behavior than a normal rules edge case. However, without engine source or the ability to inject exact internal state, we cannot determine the root cause.

---

## Suggested way to confirm

This probably requires engine source access or the ability to re-run from an exact internal state.

A useful confirmation would be to re-run the engine from the exact internal state at step 86 of the bug replay multiple times.

Possible outcomes:

* If it always fails to evolve:

  * this would suggest a deterministic bug in the Rare Candy resolution path for that internal state.
* If the result varies:

  * this would suggest non-determinism, such as uninitialized state or ordering-dependent behavior.

We only have observation-level replays, so we cannot perform this test ourselves.

Thanks for the detailed post! I tried to reproduce it, and I think the trigger is Bronzong's Evolution Jammer.

In the failed case, the turn before, your Active was hit by Evolution Jammer. So on that turn the player cannot evolve from hand. But the two evolve paths behave differently:

normal evolve menu: it correctly hides the evolve option when you are jammed.
Rare Candy: it still shows the evolve option even when you are jammed. If you pick it, the Rare Candy is discarded but no evolution happens.
I think this matches your findings. It is rare because Evolution Jammer is not a common card, and the effect only lasts 1 turn. And no board/hand feature can tell it apart, because the "cannot evolve this turn" state is not in the observation.

I tested it like this: let the opponent hit my Active with Evolution Jammer, then next turn use Rare Candy to evolve a Basic into its Stage 2.

with jammer: 100+ plays, every time the Rare Candy is used but no evolve (the Pokemon stays Basic, the candy goes to discard).
without jammer (control): the same play evolves every time (hundreds of plays, 0 fail).
So maybe the fix is: when the player is under Evolution Jammer, the Rare Candy evolve should also be blocked (or the candy should not be consumed), same as the normal evolve menu already does.

Hope this helps!
