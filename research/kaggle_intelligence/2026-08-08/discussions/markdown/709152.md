Hello Kaggle team and fellow competitors,

I am currently building a Deep Reinforcement Learning pipeline (PPO via Stable-Baselines3) to train an agent locally/in notebooks via self-play against a heuristic opponent. However, I have run into a severe memory leak originating from the competition's C++ bindings.

**The Issue**: When running continuous, sequential matches in a single Python process, the system's RAM slowly but permanently increases over time. After roughly 50,000 simulated matches (~1,000,000 env.step actions), the process completely exhausts the 30GB Kaggle Notebook RAM limit and the kernel crashes (OOM).
Context:

**The issue** occurs even if the Neural Network is kept entirely isolated.
It appears that cg.game.battle_start() and battle_select() allocate memory in the C++ engine (libcg.so) that is never properly freed or hooked to the Python garbage collector when the match finishes and a new one is initialized.
Because the C++ engine retains orphaned data from previous matches, the RAM usage scales linearly with the number of games played.
Temporary Workaround: For anyone else training RL models, the only current workaround is to implement a CheckpointCallback to save your model every 100k steps, allow the kernel to crash, restart the session to flush the RAM, and resume training from the checkpoint.

**Request: **Could the engineers please check the libcg.so source code for any missing destructors, orphaned pointers, or memory cleanup issues when a match concludes? A patch for this in the starter kit would be immensely appreciated by everyone trying to train machine learning models!

Thank you!

I may have found a related or possibly separate leak source.

In the stack trace I encountered, the crash happens during `finish()` when visualization data is generated:

```python
File "kaggle_environments/envs/cabt/cabt.py", line 90, in finish
    vis = json.loads(visualize_data())

File "kaggle_environments/envs/cabt/cg/game.py", line 75, in visualize_data
    return lib.VisualizeData(Battle.battle_ptr).decode()
```

The related binding appears to be:

```python
lib.VisualizeData.restype = ctypes.c_char_p

def visualize_data() -> str:
    return lib.VisualizeData(Battle.battle_ptr).decode()
```

If the native `VisualizeData()` function allocates and returns a new `char*` buffer for the visualization JSON, using `ctypes.c_char_p` as the return type can cause a memory leak.

With `ctypes.c_char_p`, Python converts the returned pointer into a Python bytes/string object. However, the original native pointer is no longer available on the Python side, so it cannot be passed back to the C++ library for deallocation.

Since the visualization JSON can become several MB depending on match length, this could accumulate quickly during long sequential self-play or RL loops. This may explain why memory usage keeps increasing across matches and eventually ends in `MemoryError`, `std::bad_alloc`, or `WinError 0xe06d7363`.

A safer binding would be something like this, assuming the native side exposes a matching free function:

```python
lib.VisualizeData.restype = ctypes.c_void_p
lib.FreeStringData.argtypes = [ctypes.c_void_p]
lib.FreeStringData.restype = None

def visualize_data() -> str:
    ptr = lib.VisualizeData(Battle.battle_ptr)
    try:
        return ctypes.string_at(ptr).decode("utf-8")
    finally:
        lib.FreeStringData(ptr)
```

The important point is that the returned buffer should be freed by a native function using the same allocator that created it.

Another useful workaround would be to skip `visualize_data()` generation entirely when visualization/debug output is not needed. For long local RL/self-play training, avoiding visualization JSON generation could significantly reduce memory pressure even if this is not the only leak source.

This may not be the only issue in `libcg.so`, but `VisualizeData()` looks like a concrete place worth checking.
